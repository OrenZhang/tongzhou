## 待集中处理：连接中心与统一认证

记录日期：2026-10-02。状态：需求收集中，尚未实施。用户确认先记录方案，继续补充其他问题，最后统一安排和处理；当前不启动功能改造。以下为已讨论的设计方向，具体范围在集中处理时汇总。

### 连接中心

- 将「模型连接」扩展为「连接中心」，包含连接器、账号与授权、认证记录。
- 区分连接器定义、账号与凭据、能力与权限、认证事件、浏览器登录环境，支持同一服务多个账号。
- 连接器按模型、代码平台、工具、网站分类；从某服务进入管理，只显示该服务自己的账号与认证。
- 聊天模型选择只展示模型能力；仓库、MCP 和网页能力由插件页统一管理，不混入模型下拉框。

### 待接入服务

- OpenCode Go：优先使用官方订阅 API Key、模型目录和按模型选择的接口；保留客户端标识与稳定会话标识。
- GitHub：仓库、Issue、PR 等能力；区分 GitHub API 授权与本地 Git 推送凭据，分别检测状态。
- GitHub Copilot：通过正式 SDK / 授权单独接入和验证订阅权益，不能由 GitHub 登录成功推断可用。
- GitLab：支持 GitLab.com 和自建实例，OAuth PKCE / 访问令牌；AI 订阅能力另行核验。
- 其他订阅认证通过适配器扩展，不承诺任意网页登录或订阅都能直接调用模型 API。

### 账号、状态与连接测试

- 支持个人 / 公司等多个账号，凭据仅通过引用交给受控适配器，认证记录不保存 Token 或 Cookie 原文。
- 分别展示服务连通、身份验证、资源权限、模型 / 订阅权益、实际调用结果。
- 密钥已保存不代表已验证；网络失败显示无法验证，缺少额度接口显示额度未知。
- 记录最近验证、刷新、过期、退出和错误原因，支持重新授权、解绑和清理。
- 真实推理测试明确可能计费；账号登录与能力权限检查不混为一个成功标志。

### 浏览器登录态

- 支持用户在同舟独立浏览器环境登录并持久化，按账号隔离 Cookie、LocalStorage、IndexedDB 等站点数据。
- 支持关联站点、最近验证、重新登录、退出和清除数据；不把 Cookie 保存视为永久登录保证。
- Agent 使用受控浏览器能力，不获得原始凭据；远程网页与同舟主界面的特权接口隔离。
- 优先正式 OAuth / API；网页会话仅用于相应网页操作，不自动转为模型订阅或 API 权限。
- 首版优先直接登录并保存环境；已有 Cookie 的按站点显式导入作为后续高级能力评估。

### 迁移与实施顺序

1. 拆认证层与连接中心，迁移现有模型连接，保留原连接标识、账号数据与聊天历史。
2. 接入 OpenCode Go、GitHub、GitLab，分别验证模型、仓库与本地 Git 能力，再增加 Copilot。
3. 按需通过浏览器工具插件提供网页操作能力。

会话独立于模型与账号；每轮固定连接器、账号、模型和权限。账号切换后使旧引擎连接失效，保留可移植历史，不转移旧账号凭据、浏览器登录态或工具权限。已有同会话切换、审批和取消流程需回归验证。

分析依据：[OpenCode Go](https://opencode.ai/docs/go/)、[GitHub OAuth](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)、[Copilot SDK 认证](https://docs.github.com/en/copilot/how-tos/copilot-sdk/auth/authenticate)、[GitLab OAuth](https://docs.gitlab.com/api/oauth2/)、[Electron Session](https://www.electronjs.org/docs/latest/api/session)。实施时重新核对最新接口。

## 待集中处理：移除自动规划模式与多余对话流程

记录日期：2026-10-02。状态：已定位代码触发点，仅记录，待用户补充完问题后统一实施。

### 用户反馈与现象

普通聊天、未关联项目，使用「Kimi · 账号授权 / K2.8 Preview」发送「你好」，回复却称「当前进入了规划模式」，并接着输出「好的，不打扰你了」等用户没有表达过的结束语。用户要求去掉这层内置规划逻辑，不让普通对话被强制套入规划、澄清或任务流程。

### 已确认原因与待核验项

- `electron/core/runtime/task-scheduler.ts` 的 `nativeRun` 当前在只读 Agent，或无项目且未启用公共工具时，主动选择 `plan` 并发送 `session/set_mode`。这把工具权限限制与引擎规划模式耦合，影响 Kimi / MiniMax 的回复行为。
- 同一流程又在普通聊天提示词中要求「不启动规划或澄清工作流」，与实际设置的引擎模式冲突。仅补提示词或隐藏工具条没有移除底层触发点。
- `tests/services/accounts/native-engine.test.ts` 目前还断言普通聊天使用 `plan`，修复时需要同步调整这一旧预期。
- 截图中额外结束语的具体来源尚未确认；需结合原生事件、被拒绝的澄清工具调用及历史注入复现，不能仅凭截图断定为某个工具导致。

### 修复方向

1. 移除同舟按「普通聊天 / 只读」自动进入规划模式的逻辑；默认直接响应用户，不预设必须规划、必须澄清或必须先提供具体任务。用户主动要求制定计划时可以正常给出文字方案，无需强制切换引擎模式。
2. 将回复行为与工具权限拆开。无项目默认不开放文件 / 终端能力；只读 Agent 继续限制写入；用户启用的 MCP / 电脑工具仍按独立权限和审批执行。不能简单把 `plan` 改成 `default` 后放开引擎内置工具。
3. 核实 Kimi / MiniMax 各自的工具禁用和审批能力，特别是无需请求审批就可能执行的读取或内部工具。优先通过引擎正式配置约束工具；不能仅依靠提示词或拒绝 ACP 权限请求声称完成隔离。适配器无法满足约束时明确显示能力限制，不擅自切换账号、计费方式或服务。
4. 精简自动注入的规划、角色和工作流提示，检查默认助手指令及内置澄清工具。不让拒绝或不支持的工具交互被当成用户回答，也不生成用户没有表达过的取消或结束意图；不采用删除回复关键词的文本过滤来掩盖问题。
5. 更新会话复用条件，权限或对话策略改变后重新创建原生引擎会话，防止沿用已经处于规划模式的缓存。保留原会话 ID、用户消息和历史结果；不批量删除已有对话。

### 验收

- 新建普通会话发送「你好」「你会什么」「帮我润色这段话」，直接自然回答，不自动宣布规划、不索要项目、不触发强制澄清流程，也不擅自结束对话。
- 连续多轮、重启恢复、旧规划会话继续、切换模型 / 供应商均保持上述行为。
- 覆盖 Kimi、MiniMax 适配器及真实服务复现；直接 API / Codex 普通聊天做行为回归，不假定所有引擎都有同一根因。
- 项目写入审批、只读 Agent、团队只读限制、公共插件与电脑工具权限、停止及取消仍有效。

## 待集中处理：通过会话操作同舟自身的所有模块

记录日期：2026-10-02。状态：需求收集中，仅记录分析与修复方向，等待统一实施。

### 用户目标

会话成为客户端的操作入口。用户可直接询问「有哪些 MCP」「有哪些 Agent」，也可通过自然语言管理连接、账号、插件、Skills、Agent、项目、会话、运行记录和设置，不必逐页打开界面。范围覆盖各模块实际具备的操作，不止查询列表。

### 当前缺口

`TongzhouAPI` / 主进程 IPC 已有多数界面操作，但模型侧 `ToolScope` 目前只连接外部 MCP、Skills 和电脑工具，未提供统一的客户端管理能力。不能靠模型记忆回答本地配置，也不应通过电脑点击自己的 UI 或直接改 SQLite 来代替正式管理接口。

### 设计方向

- 抽取主进程业务服务与命令注册表，UI IPC 与会话内置工具共用校验、权限、事务和结果；模型不能任意调用 IPC、执行主进程代码或操作数据库。
- 按模块建立「查询 / 创建 / 修改 / 删除 / 打开页面 / 测试 / 停止」能力矩阵。未支持的操作明确说明，不声称执行成功。注册表返回类型化结果、对象 ID 与实际状态，必要时附打开对应界面的入口。
- 只读查询直接返回真实当前数据，不额外弹确认：例如列出 MCP、Agent、Skills、可用连接、授权状态及当前运行。区分已安装、已启用、当前 Agent 获准使用，列出插件不应顺便启动全部 MCP 服务或访问所有账号网络接口。
- 配置修改遵循已有授权和审批策略；删除、退出账号、连接外部服务、真实计费测试等操作展示具体对象与影响。密钥和 Cookie 通过安全输入 / 登录流程配置，模型只能看到凭据是否存在及验证状态，不获得原文；批准 / 拒绝审批始终由用户决定，Agent 不能批准自己。
- 当前任务使用冻结的模型、账号和工具权限。自身配置修改默认作用于下一轮，不允许本轮自行扩权。现有 `requireIdle` 阻止运行中修改插件，需要改为针对受影响资源处理；必要时排队到任务结束后应用，避免模型调用管理工具后必然被自己的运行状态阻止。
- 自己停止、删除当前会话或重启客户端等操作先保存结果，再终止 / 延后处理，避免等待当前任务取消造成死锁。操作使用幂等标识，重试不重复创建或删除。
- 变更后同步刷新 UI；操作记录与同一会话关联。跨模型可继续查询同一份本地状态，切换后不重复执行历史管理操作。
- 内置能力目录按模块发现、按需提供详细工具定义，避免一次注入所有模块 schema 增加上下文和首字延迟；用户明确查询配置时只取相关字段和必要分页。

### 验收示例

- 「列出已配置的 MCP，并告诉我哪些已启用」：直接返回真实清单；无插件时明确为空，不虚构。
- 「有哪些 Agent，各自用哪个模型、能使用什么工具」：返回默认配置与权限，区分继承值和当前会话的手动选择。
- 「创建一个只读代码审查 Agent」「停用某个 MCP」「打开 GitLab 认证」「归档这个会话」：走正式业务服务，完成后界面和实际数据一致。
- 当前任务修改自身工具权限只影响后续任务；拒绝审批、重启恢复、同名对象歧义、重复请求和自我停止均有明确结果。

## 待集中处理：聊天延迟、思考状态与事件展示

记录日期：2026-10-02。状态：已核对代码，未做本次性能基准；记录后待统一实施。此项与「去掉自动规划模式」不同：移除强制规划流程，同时保留真实的处理状态与供应商公开的思考事件。

### 当前发现

- `src/components/components.tsx` 只有在流式助手消息已存在且正文为空时显示「正在思考…」。Kimi / MiniMax 的 `nativeRun` 与 Codex 适配器均在收到第一段正文时才创建助手消息，初始化和首字等待阶段缺少对应占位与阶段反馈。
- `AppEvent` 没有统一运行进度或思考事件。ACP 当前仅处理正文和部分工具更新；Responses 仅输出正文增量；Anthropic thinking 内容虽为协议续接保存，但没有流式展示；Gemini thought 内容未接入展示。是否存在具体可公开事件，需按固定引擎 / 接口版本核验。
- `scope.prepare` 在推理前连接已启用 MCP 并获取目录；原生新会话还涉及启动、认证、模型目录与模式设置。普通原生聊天已有有限复用，但启用公共工具后不复用，Codex 每轮建立新分段，可能增加等待。
- 当前 Run 主要记录开始 / 结束时间，缺少分阶段耗时。以上是可确认的代码路径与候选开销，不能据此认定实际慢在网络、模型思考或某个插件。

### 状态与事件展示方案

1. 发送后立即显示本轮状态占位、已等待时间和停止入口，独立于是否收到模型正文。区分本地发送中、已接收和发送失败，避免重复点击造成重复任务。
2. 增加统一 `RunEvent`：准备上下文、准备工具、连接引擎、等待模型、思考、输出正文、工具调用开始 / 完成、等待用户批准、取消、失败、完成。事件带 runId、序号、来源与时间，避免跨会话、晚到事件和重连重复覆盖状态。
3. 只显示实际发生的阶段，不按定时器伪造「正在搜索」「正在读取文件」或进度百分比。无模型事件时显示「等待模型响应」，收到明确思考事件才细化为「思考中」；阶段耗时与思考耗时分别计算，未知不能标为零。
4. 提供可折叠的「处理过程」区域，流式呈现供应商明确公开的思考文本 / 摘要、工具活动与耗时；正文单独展示。隐藏推理、加密内容和协议签名不解析为用户可读思考，也不编造思考过程。
5. 按各协议 / SDK 的正式事件逐一适配，缺少公开思考能力时降级为真实阶段和计时。用户可展开过程，但不因此给普通聊天增加内置规划步骤或额外模型请求。
6. 状态和公开过程使用独立存储 / 展示结构，不混入聊天正文，不默认作为跨供应商历史重复注入；供应商要求回传的协议字段继续按原有绑定规则保存。设置长度上限、批量落盘与清理策略，避免日志无限增长。
7. 取消、异常或完成后立即结束计时和动画；保存已返回正文与适当的过程记录。重启后的未完成运行标记中断，不永久显示思考中。隐藏普通引擎噪声工具条的已有需求继续保留，详细事件放在折叠区域。

### 实际性能排查与优化

- 记录发送、本地受理、上下文准备完成、MCP 准备完成、引擎启动 / 认证完成、请求发出、首事件、首正文、末正文、任务完成等时间点；区分首事件延迟、首字延迟、生成速度和总耗时。
- 以同账号、模型、提示与网络条件比较冷启动 / 热启动、普通聊天 / 插件聊天、短历史 / 长历史，统计多次结果；不凭一次请求承诺固定提速比例。
- 优先移除不必要的规划与重复探测；缓存带有效期的模型 / 工具目录，设置变更与认证失效时明确失效。用户未启用的服务不连接；无关状态查询不阻塞当前模型请求。
- 评估隔离明确的引擎连接复用、MCP 连接复用与插件准备并发。连接可复用，但每轮权限、取消信号、工具桥接令牌与账号必须重新绑定；不能为了提速跨账号共享授权。
- 将预热放在后台且按需进行；加载失败不得静默丢弃任务要求的工具。优化 UI 增量更新、SQLite 写入频率和长历史加载，完成及中断时保证最终内容落盘。
- 上游慢或长时间无事件时显示真实等待及停止选项；默认不偷偷切换供应商、不额外发起付费探测、不重放有副作用的工具调用。

### 验收

- 发送后一个正常 UI 更新周期内出现状态反馈，不等首段正文；思考阶段有公开事件时能流式显示，没有时不伪造。
- 验证长时间无正文、只有公开思考事件、工具多轮、等待审批、插件连接慢、首字前取消、失败和重启恢复。
- 多会话并行、切换供应商、重连及重复 / 乱序事件不会串状态、重复展示或保留错误计时。
- 用一致条件记录优化前后的阶段耗时；「更快」与「反馈更及时」分开验收，不能只加动画就算性能修复。

## 待集中处理：Agent 初始化与说明文件生成

记录日期：2026-10-02。状态：需求收集中，仅记录，不开始实现。用户要求增加 Agent 初始化能力，生成 Agent 的 Markdown 说明文件。

### 目标与入口

- 提供「初始化 Agent / 生成 Agent 说明」入口，同时支持会话指令，例如「帮这个项目初始化 Agent，生成 agent.md」。
- 按用户所述记录 `agent.md` 文件生成需求，同时识别项目已有的 `AGENTS.md` 等说明文件。初始化时明确目标文件与作用范围，不擅自重命名已有文件、不生成相互冲突的重复规则；兼顾 Windows / macOS 文件名大小写差异。
- 区分项目工作约定与客户端 Agent 角色配置。初始化项目说明可关联现有 Agent，也可按用户要求新建角色；生成文件不应强制绑定某个模型或账号。

### 初始化行为

### Hook 与发送链路

- 复用运行事件注册表，提供结构化 Hook：任务完成 / 失败 / 取消、等待审批 / 输入、产物就绪，以及按需节流的阶段进展。普通用户配置「事件 → 条件 → 渠道 → 消息模板」，不必编写脚本；首版不执行任意 Shell Hook。
- 事件携带 eventId、sessionId、runId、来源、时间、状态和必要摘要。运行状态落盘后通过持久化发送队列分发；UI 操作、模型主动发送和自动规则共用服务与校验。
- 主动发送使用明确的目标 ID 与本次请求 ID，遵循用户已经给出的发送授权，不反复确认同一目标和内容。用户说「以后都通知」才创建长期规则，不能从一次发送推断永久授权。
- 自动通知使用状态和已有结果生成模板，避免每次额外请求模型。默认不发送完整聊天、系统指令、工具日志、密钥、Cookie 或本地路径；摘要内容范围可配置，附件和敏感内容走明确授权。
- 相同事件、规则和目标去重；保存待发送、已提交平台、失败、结果未知等状态与错误原因。HTTP 成功仍需检查平台业务结果；平台接收不等于对方已读。
- 限流和明确可重试失败使用退避及次数上限；请求超时但可能已送达时标为结果未知，没有平台幂等保障就不盲目重发。提供查看、取消待发和手动重试入口，标注重复发送风险。
- 通知事件不再触发通知规则；机器人自身消息、平台重复回调和回复回声过滤，避免形成循环。通知失败不回滚已完成任务，也不阻塞会话正文输出。
- 全局停用或会话规则关闭后再次检查待发任务，取消尚未发出的相关消息。应用退出 / 电脑休眠时本地队列无法持续工作；重启后按过期策略恢复，不突然批量补发。需要全天候运行时再单独设计常驻服务或自托管中继，不默默部署云服务。
- 规则、发送日志和渠道状态可通过会话查询 / 修改，与「会话操作客户端」待办共用业务服务。远端通知使用可读会话标题和 ID；本地深链接只能作为本机入口，不能承诺手机能打开本地会话。

### 平台接入与优先级

1. 第一阶段实现渠道模型、持久化队列、主动发送及完成 / 失败通知，优先提供经验证可用的官方扫码接入；以实际账号可开通的机器人类型为准。Webhook / 应用凭据作为高级接入方式保留，不把手动填写密钥作为所有渠道的默认首页。首批文本 / 摘要，后续扩展卡片、附件和指定成员提醒，不默认 @所有人。
2. 第二阶段补充应用级机器人、单聊 / 更丰富群消息与双向会话。钉钉官方文档明确区分群 Webhook 的单向通知与应用机器人的收发能力，后者支持 Stream；不能把两种能力混为一个配置。
3. 飞书应用事件订阅 / 长连接、企业微信应用或智能机器人接收方式分别核验当前官方接口、账号条件、SDK 及权限。此次企业微信官方文档读取失败，暂不承诺其接收模式或与其他平台相同的能力。若必须公网回调，单独说明部署要求。
4. 双向阶段使用「平台租户 + 机器人 + 群 / 话题 + 已授权发送人」映射会话，保留来源标记；无明确绑定时列出允许访问的会话供选择，不默认进入最近会话。多用户会话隔离、验签、防重放及去重必须落地，外部消息不能因被转发就获得本地全部操作权限。
5. 远端审批作为独立后续能力；普通群回复「同意」不能直接批准电脑控制或写入。先支持通知等待审批并引导回客户端处理。

分析依据：[飞书自定义机器人指南](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)、[飞书事件订阅配置](https://open.feishu.cn/document/server-docs/event-subscription-guide/event-subscription-configure-/request-url-configuration-case)、[钉钉机器人概述](https://open-dingtalk.github.io/developerpedia/docs/learn/bot/overview/)、[钉钉 Stream Node SDK](https://github.com/open-dingtalk/dingtalk-stream-sdk-nodejs)。[企业微信群机器人官方文档](https://developer.work.weixin.qq.com/document/path/91770)留待实施时核验。飞书页面此次正文提取有限，不据此承诺全部接口可用。

### 补充：扫码接入优先

用户进一步要求渠道尽量直接扫码对接。目标流程为「选择平台 → 扫码创建 / 关联机器人或授权应用 → 选择允许的群 / 接收人 → 验证 → 显示已连接」，尽量免去复制 App ID、Secret 和 Webhook 的步骤。

- 扫码方案逐个平台验证，不能仅把一个设置网址生成二维码就称为完成授权。优先复用官方提供的机器人创建、应用安装和授权流程；扫码登录只证明身份，仍需确认消息发送权限和目标可达。
- 飞书优先做可行性验证：飞书官方 OpenClaw 插件指南已描述「扫码一键创建机器人」及关联已有机器人的流程。需进一步检查该流程对同舟的开放条件、协议 / SDK、许可证及凭据安全交付方式；这证明有官方体验可参考，不证明该专用流程能直接移植到任意客户端，也不要求用户安装 OpenClaw。
- 钉钉分别核验用户扫码登录、组织管理员授权、机器人开通三个环节，选择最短可行路径；企业微信也单独验证应用 / 机器人类型与管理员要求。尚未核验通过的平台标为待适配，不承诺三个平台都能一次扫码完成所有配置。
- 官方授权页面可在系统浏览器打开，支持返回同舟并自动更新状态。若协议支持桌面公开客户端则使用对应安全流程；若需要保密的应用 Secret 或公网回调，则明确自建应用 / 自托管授权服务方案，不在开源仓库或安装包中嵌入共用生产 Secret。
- 凭据保存到系统安全存储，二维码 / 登录 URL 不包含长期密钥。授权会话校验 state、有效期和目标账号，支持取消、过期刷新和重试；不抓取浏览器 Cookie 来代替平台消息授权。
- 状态明确区分等待扫码、已扫码待确认、等待管理员、已授权待选目标、可发送、失败 / 已过期，仅显示平台确实返回的阶段。成功后显示平台、组织、账号 / 机器人身份、可用能力和成功标志；不能仅凭浏览器已关闭判断成功。
- 目标选择只展示授权范围内可枚举的群 / 接收人；无法枚举时引导加入机器人或显式指定目标，不能将其显示为所有群均可用。测试发送明确标为外部发送动作。
- 保留「使用已有机器人 / 手动配置」高级入口，适配组织限制和自托管用户；不因扫码路径尚不可用而显示假二维码。验收覆盖 Windows / macOS、非管理员、已有机器人、授权拒绝、扫码超时、错误组织、断网与重新授权。

新增依据：[飞书官方插件扫码创建机器人指南](https://www.feishu.cn/content/article/7613711414611463386)、[钉钉应用权限与管理员授权说明](https://open-dingtalk.github.io/developerpedia/docs/develop/permission/token/browser/get_app_only_token_browser/)。以上是分析参考，本次未安装插件、创建机器人或发起授权。

## 待集中处理：会话运行中补充内容

记录日期：2026-10-02。状态：仅记录。优先按「回复 / 执行过程中追加要求」设计；同时记录在历史位置补充内容的扩展场景，不把二者混为原地改写历史。

### 当前缺口

`src/app/App.tsx` 在运行中阻止发送，`electron/core/runtime/task-scheduler.ts` 的 `start()` 也拒绝同会话并发运行。应增加专门的补充消息处理，而非只放开按钮后启动第二个竞争执行的任务。

### 补充方式

- 输入框在生成、工具执行和等待审批期间仍可编辑并提交补充，保留草稿和附件，显示补充已保存 / 待处理 / 已应用 / 失败以及生效轮次。
- 「补充当前任务」：适配器明确支持运行中 steer / 输入注入时，在支持的边界传递；不支持时显示将在下一个安全边界处理，或提供「停止后按补充继续」，不能把仅写入本地的消息标成模型已经看到。
- 「排队下一轮」：当前任务结束后按序处理，允许编辑、取消尚未消费的条目；不同时启动第二个会话运行，不将下一轮要求错误注入当前工具调用。
- 「停止并按新要求继续」：等待当前运行取消 / 收尾后，保留已输出内容和已经发生的操作结果，再结合补充继续；不重放已完成写入、通知或其他副作用。取消不等于回滚。
- 普通补充默认延续原目标；明确取消、改方向或替换任务时更新后续目标。记录采用了哪些补充，不凭补充消息自动将整个任务判定为完成或取消。

### 顺序、会话与上下文

- 每条补充有稳定消息 ID、接收序号、关联 runId、来源与消费状态；先持久化再确认，防止双击、重连及平台回调重复消费。连续补充可批量纳入下一次模型输入，但原始消息顺序与状态可追溯。
- 接入渠道后，授权的飞书等入站消息走相同队列；多来源冲突不静默覆盖。明确显示未消费消息，重启后可恢复，不能未经判断自动重跑中断的有副作用任务。
- 当前轮模型 / 账号和权限保持固定；排队消息使用的配置在执行前明确显示。切换模型或渠道目标不能导致补充丢失、跨会话串入或重复执行。
- 等待审批期间可以补充或取消任务；普通补充不被解释成审批同意。新要求改变了待执行操作时，使旧审批失效并按新操作重新评估。
- 历史位置补充优先支持「引用这条消息继续」；如果用户要改变历史上下文，则从该位置建立会话分支，保留原后续消息，不在中间插入后假装既有回复已考虑新内容。附件按同样的上下文与来源规则处理。
- 验收覆盖首字前 / 正文流式中 / 工具执行中 / 等待审批时补充、连续多条、队列编辑取消、停止续接、进程重启、模型切换和不同供应商降级；界面所示生效状态与实际发给模型的上下文一致。
