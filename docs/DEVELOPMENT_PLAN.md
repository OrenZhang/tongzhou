# 同舟集中开发计划

初始计划日期：2026-10-02；实施更新：2026-10-03。0.4.0 代码与本地验证已经执行，逐工作包状态见 [实施状态](IMPLEMENTATION_STATUS.md)，实测结果见 [验证记录](VALIDATION.md)。下文保留开发前的问题基线、设计和完整验收目标，不能将原始“未执行”描述当作当前状态。需求来源：[开发路线](ROADMAP.md)；当前实现基线：0.3.0，代码及 [既有验证记录](VALIDATION.md)。

## 1. 目标与实施原则

优先把同舟做成可连续聊天、可实际完成项目修改的工作台，再扩充连接、插件和通知。所有本次收集的待办都纳入下列工作包；需要第三方接入条件的能力有单独验证关口，不用占位页面当作交付。

- 普通聊天不要求项目或 Agent，不自动进入规划模式；Agent 初始为空，模板仅主动选用。
- 插件统一启停，所有会话和 Agent 继承；只读、项目范围、系统授权及操作审批独立执行，不增加重复勾选。
- 同舟 Session 是事实来源；切换模型、账号、引擎及补充输入不创建意外的新会话，也不重放历史操作。
- 显示真实运行状态和公开思考事件，取消 / 出错 / 等待均有反馈；不把动画作为性能优化成果。
- GUI、聊天内管理、渠道入站共用业务服务，修改后立即回显同一份数据。
- 项目开发必须完成读取、修改、执行、验证和结果检查的实际闭环。能力是否接近 Codex 以对照任务的结果判断。
- 保持 Electron + React + TypeScript，按功能边界逐步拆分；不先重写桌面壳或全量 UI。架构拆分服务于本轮功能。
- 本计划的工程阶段不注入为用户聊天的固定工作流，不以实施计划重新引入强制规划模式。

## 3. 目标结构与数据契约

调用方向统一为：界面 / 会话管理工具 / 授权渠道输入 → 业务服务 → 会话调度与能力策略 → 引擎或平台适配器。数据库是事实来源；事件负责通知界面与外部发送队列，不允许事件消费方直接改任意数据。

### 3.1 模块边界

以下为建议新增边界，实际可先在现有目录逐步抽取，不要求一次创建空模块。

| 边界            | 职责                                                              | 主要迁移来源                             |
| --------------- | ----------------------------------------------------------------- | ---------------------------------------- |
| `services/`     | 会话、项目、Agent、能力、连接、渠道等业务操作；参数 / 权限 / 事务 | main.ts IPC handlers                     |
| `runtime/`      | Run 状态机、输入队列、历史编译、引擎段与取消                      | runtime.ts                               |
| `adapters/`     | direct API、Codex、ACP 的事件和能力适配                           | providers.ts、codex.ts、native-engine.ts |
| `capabilities/` | 内置能力、MCP、Skills 目录、全局启停及调用检查                    | extensions.ts、workspace.ts、computer.ts |
| `connections/`  | 服务目录、账号、凭据引用、模型能力、授权会话、浏览器环境          | Provider / auth 相关代码                 |
| `channels/`     | 飞书 / 企业微信 / 钉钉发送适配、订阅规则、发送队列                | 新增，依赖连接及运行事件                 |
| `src/features/` | 聊天、连接、Agent、插件、渠道、项目变更等页面                     | App.tsx、Extensions.tsx；按阶段抽出      |

### 3.2 核心对象

| 对象                             | 关键字段 / 关系                                                                      | 约束                                                 |
| -------------------------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| Session                          | id、projectId?、agentId?、模型 / 账号选择、归档 / 删除状态、revision                 | 产品会话 ID 稳定；删除标记阻断晚到事件               |
| Run                              | sessionId、frozenConfig、状态、时间、输入消费位置                                    | 每会话至多一个活动 Run；终态只落一次                 |
| RunEvent                         | eventId、runId、seq、type、source、time、payload                                     | 正文、公开思考、工具事件分离；可重放展示，不重放执行 |
| InputEnvelope                    | messageId、sessionId、targetRunId?、source、mode、seq、status                        | 队列重试不重复消费；accepted 不等于 applied          |
| EngineSegment                    | sessionId、accountId、模型 / 引擎版本、threadId、historyRevision、capabilityRevision | 复用绑定账号及上下文版本；变更后失效                 |
| CapabilityDefinition / State     | id、来源、工具 / Skill、平台、配置版本、enabled、health                              | 一个启停来源；权限在每次 dispatch 再校验             |
| Connector / Account              | 服务类型 / 端点、认证方式、credentialRef、账号身份、状态                             | 登录、模型权益与业务权限分开；共享凭据不下发给模型   |
| AuthSession / AuthEvent          | connectorId、accountId?、phase、过期时间、脱敏结果                                   | 一次性 code / QR 状态不长期持久化；并发授权隔离      |
| BrowserProfile                   | accountId、独立存储分区、站点、最近验证                                              | Cookie 不进入聊天历史、认证日志或仓库                |
| Channel / Target                 | connectorRef、accountRef、平台、机器人 / 群 / 接收人、enabled                        | 发信身份和接收目标明确；全局关闭立即阻止新发送       |
| NotificationRule / Delivery      | scope、eventFilter、target、template、eventId、幂等键、status                        | 全局规则与会话覆盖去重；队列与事件事务关联           |
| ProjectChange / CommandExecution | runId、文件前后哈希、diff、命令 ID、输出、退出码                                     | 区分用户原有变更；工具成功与任务成功分开             |

迁移建议：小配置对象可暂留 objects 表；高频 RunEvent、InputEnvelope、Delivery 采用带 session/run 索引的专表。迁移版本递增且幂等，迁移前备份 SQLite 一致快照；不能在 WAL 活动时仅复制主 db 文件当备份。旧版本拒绝打开新 schema；回退使用匹配备份，不直接降版本字段。

### 3.3 运行与权限约定

- Run 生命周期：受理 → 准备 → 运行（等待模型 / 输出 / 工具 / 等待审批）→ 取消中或终态。等待输入只在实际需要时出现，不能强制每次任务先澄清。
- 输入状态：已保存 → 已排队 / 已送交引擎 → 已应用；取消和失败独立终态。没有消费确认的适配器只显示已送交或等待下一轮。
- 工具有效范围 = 全局启用能力 ∩ 当前项目 / 账号范围 ∩ 本轮冻结权限 ∩ 引擎支持。停用可收紧正在运行的权限，启用不在本轮自动扩权。
- 文件工具、MCP、原生工具各有执行来源；同一功能不同时暴露多个绕过路径。CLI 自有工具必须受其正式配置约束，无法禁用时显示能力差异，不用系统提示冒充隔离。
- UI 查询和聊天查询共用只读接口；运行中修改设置写新 revision，影响资源的销毁或重建在安全点进行。停止当前会话不得同步等待调用自己的 Run。

## 4. 工作包与依赖顺序

顺序：P0 基线和验证 → P1 聊天基础 → P2 会话连续性 → P3 能力与客户端管理 → P4 连接认证 → P5 渠道 → P6 项目开发完善 → P7 综合测试修复 → P8 发布。P4 的外部扫码 / 账号验证在 P0 提前探路，避免接近交付时才发现接入条件不满足。

各阶段只跑与变更相关的必要回归；完整的真实项目测评安排在功能调整之后。前一阶段出现数据丢失、会话串线等阻断问题时先修复，不带病扩功能。

### P0：基线、迁移设计与协议验证

- P0.1：保存当前版本、依赖锁、测试条件与可复现问题清单；建立独立 TONGZHOU_USER_DATA 和测试项目目录，不修改用户历史数据库。
- P0.2：准备脱敏的旧库迁移样本：未修改默认角色、自定义角色、多个供应商、无项目聊天、未完成任务、工具结果和附件。冻结数据不变量与迁移顺序。
- P0.3：给当前链路建立时间点采集基线，分准备、工具发现、引擎启动、认证、请求、首事件、首正文、完成。采样不保存凭据或原始私人对话。
- P0.4：核验锁定的 Codex 0.160.0 与 Kimi / MiniMax 版本的 resume、steer、公开思考、工具限制、取消和账号目录隔离。当前文档支持不等于锁定二进制支持。
- P0.5：验证飞书扫码流程能否合法、独立地接入同舟；企业微信 / 钉钉按官方渠道核验。记录需要管理员、应用注册、公网回调或服务端的具体条件。禁止在产品中嵌入共用 Secret。
- 交付：基线报告、兼容能力表、迁移用例及每项未知问题的结论 / 待验证标记。
- 完成条件：主要技术路线有证据；不可用能力有明确降级，不先画成已支持。

### P1：先修普通聊天与反馈

- P1.1：agentId 可空，抽取基础 RunContext，清除 builder 默认依赖、默认团队选择和自动种子回填；旧角色按来源 / 内容识别，保留用户改过的角色和历史引用。
- P1.2：移除按无项目 / 只读自动进入 plan 的行为；依 P0 结果使用独立工具控制。审查普通聊天、角色与引擎指令冲突，复现并修复不合语境的结束语。
- P1.3：发送受理即生成运行占位，显示等待、耗时、停止；增加 RunEvent 与正文 / 公开思考 / 工具事件映射，不再只等正文创建助手消息。
- P1.4：折叠详细过程，普通聊天隐藏内部引擎噪声条；解释用户实际调用的工具、错误和等待审批。思考事件不支持时显示等待响应。
- P1.5：按基线优化无关 MCP 初始化、模型目录探测和重复认证；流式展示与落盘节流分离，结束 / 中断时确保最终落盘。
- 主要代码：store、types、validation、runtime、providers、components、App 及原生事件适配。
- 验收：无 Agent / 项目仍正常聊天；你好、润色、解释代码等用例自然回复；失败 / 停止不挂住；角色清空后重启不复活。针对真实问题更新旧 plan 测试预期。

### P2：连续会话、途中补充与删除

- P2.1：加入持久化输入队列、补充 / 排队 / 停止后继续 API 和输入框状态。支持连续多条、编辑未消费消息、取消排队；仍维持每会话一个活动 Run。
- P2.2：Codex 依据锁定协议绑定 threadId 与活动 turnId 做 steer；API 在工具 / 模型请求安全边界消费补充；不支持中的 ACP 明确排队或取消续接，不虚报即时注入。
- P2.3：同账号、模型、项目、指令、能力版本与历史连续时复用引擎段；切换供应商 / 账号后用可移植历史续接，废弃旧桥接 token、截图及不适用的协议签名。
- P2.4：记录用户目标、约束、已完成操作、待办和来源消息的 ContextCheckpoint；优先确定性提取和完整轮次。需要模型压缩时有成本 / 用量记录，原消息仍保留，摘要不提升工具输出为系统指令。
- P2.5：先支持引用历史继续，再实现显式历史分支；分支继承上下文不继承未消费任务或历史执行动作。
- P2.6：归档列表增加删除，事务处理消息、Run、事件、队列、引擎段、私有附件和子会话关系；父会话删除默认连同其内部团队子任务，独立分支保留并解除来源引用，界面显示范围。删除不清理项目源文件。
- 验收：跨模型多轮 / 取消后继续 / 重启恢复不丢输入、不重复写入；运行中删除等待收尾，晚到事件不复活；同名会话不串队列。

### P3：统一插件、内置工具、客户端管理与 Agent 初始化

- P3.1：能力注册表及全局开关，删除 AgentTools 重复勾选和默认助手工具弹窗。旧配置保留迁移来源，显示全局生效范围；不自动把旧权限并集静默开启。
- P3.2：工具目录缓存带版本、检查时间和健康状态；按需连接 MCP、发现详细 schema、加载 Skill。插件随附 Skill 跟随同一个开关，独立 Skill 单独管理。
- P3.3：电脑、文件、终端卡片展示工具清单和阻塞原因；按钮独立 loading、成功 / 失败回显；电脑自检使用测试窗口，停止入口显示任务数。
- P3.4：抽取 Service 层，注册列举 / 创建 / 更新 / 删除 / 打开 / 验证等客户端业务命令；先交付 MCP、Agent、连接、会话等现有模块，后续新模块必须同时接入聊天命令。
- P3.5：Agent 初始化读取项目事实并生成 agent.md，识别 AGENTS.md 与大小写冲突，展示差异，不覆盖独立编辑。统一加载来源 / 优先级并防止引擎重复加载；不强制创建 Agent。
- P3.6：精选 MCP：Fetch / Git 优先，Playwright 随浏览器能力验证，Memory 可选关闭，Time 复用运行时，文件 / 电脑复用已有能力。检查依赖、许可证、平台包和更新来源，离线安装失败明确显示。
- 验收：无 Agent 情况下工具可用；全局关闭后下一次调用被拒绝；查询自身配置返回真实数据；配置修改不会被当前 Run 的全局空闲锁阻止；Win / Mac 权限状态不伪报成功。

### P4：连接中心、账号与浏览器登录态

- P4.1：拆 Connector、Account、AuthEvent，保留旧 Provider ID 映射。模型下拉只列模型，进入具体服务的管理界面只看到该服务。
- P4.2：修复并实测 ChatGPT 浏览器 / 设备授权、Kimi / MiniMax 授权；账号读取、模型发现、真实推理分别验证。UI 展示已授权成功标志、过期、失败与重试，不把网页打开等同于成功。
- P4.3：同服务多账号隔离 home、keyring 标识 / 凭据引用、缓存和原生进程；退出仅影响对应账号。确认各 CLI 支持方式后再迁移旧认证目录，不复制未知共享 keyring 状态。
- P4.4：接入 OpenCode Go、GitHub、GitLab；GitHub API 与本地 Git 凭据分别检测；Copilot 和其他订阅按官方接入方式单独实现，未验证权益不显示可调用。
- P4.5：实现独立浏览器 Profile 的创建、登录、关联账号、清理和退出；与 Playwright 的执行环境确定统一的持久化归属，不能默认互通 Electron / Chromium Cookie。Cookie 手动导入作为高级后续项保留。
- P4.6：账号 / 模型目录缓存、能力发现、认证记录脱敏、失败分类、取消过期扫码及并发授权隔离。
- 验收：多个账号不串身份；更换认证不丢会话；单服务入口正确过滤；错误账号 / 额度不足 / 网络错误有区别；浏览器重启保存登录态、清理确实失效。

### P5：渠道扫码、通知和双向会话

- P5.1：渠道页复用连接中心账号和能力开关；实现目标、规则、发送记录及队列。范围支持全局 / 项目 / 会话；同一渠道供所有会话使用，但未订阅时不自动转发。
- P5.2：按 P0 结论落地官方扫码接入，优先飞书；钉钉 / 企业微信分别实现实际可用路径。扫码、待管理员、授权、目标选择和可发送状态逐步反馈；手动凭据放高级入口，无法扫码时如实展示。
- P5.3：统一主动发送与自动 Hook。支持「把这段结论发到某群」「这次完成后通知」「这个会话失败时通知」；分别形成即时动作、单次订阅和长期规则，不混用授权范围。
- P5.4：状态事件及出站任务通过事务 outbox 衔接；租约领取、幂等去重、业务错误、限流、超时结果未知和可取消队列。启停与删除会话时清理待发任务；已发外部消息不假装撤回。
- P5.5：后续子阶段接应用机器人入站，把授权发送人 / 群 / 话题绑定到指定会话，并复用 P2 输入队列。防重复回调和机器人回环；群里普通回复不直接变为本地审批。
- P5.6：本地客户端离线 / 休眠时显示停止服务的实际边界；全天候服务、自托管中继和远端审批另列扩展，不让首版偷偷依赖云后台。
- 验收：三个渠道分别验证支持矩阵；扫码成功后能发到正确测试目标，关闭后不再发；一个会话多目标、多会话同目标不串内容；应用型收消息能力与 Webhook 单向能力明确区分。

### P6：项目开发链路补齐

- P6.1：项目搜索与读取：文件 / 文本搜索、忽略规则、分段读取及行号、输出分页 / 上限；不依赖模型用 Shell 猜目录。处理中文路径、空格、CRLF、超大文件和符号链接边界。
- P6.2：补丁编辑：支持精确替换 / 多文件 patch，绑定模型实际读过的文件版本或哈希，避免模型读取后文件已变化却按过时内容覆盖。校验上下文、不匹配则重新读取，不静默模糊匹配；已有整文件写入保留兼容但用于适合场景。
- P6.3：命令执行：结构化 commandId、cwd、exitCode、stdout/stderr、超时 / 取消状态；运行中增量输出，长命令可显式继续等待 / 停止。升级当前固定两分钟流程，保留时间与输出上限，停止需回收子进程。
- P6.4：变更查看：建立任务开始时的仓库状态基线，展示运行相关修改和当前工作区 diff；列出新增未跟踪文件，区分用户原有修改。先交付可读 diff 和定位文件；部分暂存 / 撤销能力以明确范围和冲突检查逐步加入。
- P6.5：测试与错误闭环：将真实命令退出码、测试失败、构建诊断返回模型；保留原始证据，支持继续修复并重跑相关检查。最终回复链接实际文件与执行结果，不能根据“工具调用完成”推断“测试通过”。
- P6.6：项目说明和长任务续接：加载用户明确维护的说明，摘要记录目标、限制、修改、验证和未完成事项；上下文压缩 / 切换供应商后仍能重新读取当前文件，不拿旧摘要当实时文件内容。
- P6.7：统一工具适配策略：通用 API 使用同舟项目工具；Codex / ACP 优先保留成熟原生项目执行，但把结果、审批和改动证据接入统一事件。实际工具边界不同则显示差异，不能宣称完全相同沙箱。
- P6.8：多会话写入协调：相同项目至少检测并发写入和文件版本冲突；写入团队不直接共享目录并行改。已有只读团队保持可用；worktree 隔离与补丁整合作为 E1 扩展接入，不为对齐 Codex 名义扩大本轮同时写入范围。
- 验收：能发现错误文件、最小修改、运行真实测试、从失败恢复并展示真实 diff；未提交内容不丢失，拒绝 / 取消后不继续操作。先用固定本地协议替身验证工具，再进入真实模型项目测评。

### P7：集中测评 → 定位修复 → 回归

- P7.1：功能合并后重新执行单元 / 协议 / 迁移测试和 Electron 桌面回归；全部使用隔离数据与固定输入。
- P7.2：按第 6 节真实任务运行聊天、项目开发和渠道矩阵，记录失败样本，不挑选最好的一次结果。
- P7.3：为每个失败记录复现条件、引擎 / 模型、任务 ID、日志及预期；按客户端 / 模型 / 网络 / 账号 / 平台依赖分类，先修数据损坏、串号、重复副作用等阻断问题。
- P7.4：每次修复补最小必要回归，重新执行失败任务及受影响的相邻用例。禁止改弱任务验收条件来“修绿”，不因为一轮测试结束就关闭仍存在的问题。
- P7.5：按相同配置复测性能和 Codex 对照，汇总通过、失败、未验证及差距。不支持组合保留明确标记，不能合并进通过率。
- 交付：脱敏测试报告、缺陷与修复记录、模型 / 平台能力矩阵、Codex 对照结果。若门槛未达到，继续修复和复测，不进入完整功能发布。

### P8：跨平台交付与 GitHub 维护

- P8.1：Windows x64 安装包和 macOS 的目标架构分别构建 / 安装验证；核对内置 CLI、Node 原生依赖和浏览器依赖，不以 Windows 成功推断 Mac 成功。
- P8.2：验证独立安装目录、中文 / 空格路径、干净配置、旧库升级、卸载后数据策略、系统权限与停止快捷键。Mac 签名 / 公证条件单列，缺失时明确分发限制。
- P8.3：更新 README、架构、发布说明、迁移与验证文档；区分实际支持和候选接入。清理过时断言，例如已推送仓库仍写“未配置远端”，以及仍描述强制 plan 的架构章节。
- P8.4：复用现有 GitHub CI / release 工作流，真实账号测试与无密钥 CI 分开；不将真实登录态、Cookie、聊天、截图和测试输出提交仓库。源码测试夹具只使用合成 / 脱敏数据。
- P8.5：后续实施按工作包提交和推送到 OrenZhang/tongzhou，发布前核对远端实际分支、构建产物与版本。本次规划阶段只写文档，不把计划条目标成已实现。

### 6.4 如何比较 Codex

- 对照轨道 A：同舟 Codex 引擎与官方 Codex 使用同一模型、可比推理配置、账户、网络、初始提交和任务预算；记录双方实际版本、权限与原生工具差异。尽量隔离时间并交错运行以减少网络波动。
- 对照轨道 B：同舟 Kimi / MiniMax / 直接 API 在相同项目任务下测可用性与质量。它衡量组合表现，不能据此断言某个客户端架构更差或任意模型等于 Codex。
- 优先对照官方桌面端的聊天 / diff / 中途补充体验。若只有官方 CLI 可用，报告标为 CLI 开发链路对照，桌面交互仍未对照；不替换名称。
- 初轮每任务至少 3 次独立运行，所有重试和人工介入计入结果；账号缺失、限流、网络中断单列。样本较少时只给描述统计，不宣称统计显著或普遍能力等同。
- 记录完成率、独立测试通过率、无关修改、虚构成功次数、越界 / 重复副作用、人工干预次数、首字与总耗时，以及接口实际返回的用量。未知用量不填零，不假设各引擎 token 可直接比较。
- 临时目标：基础任务 D01–D07 每项至少 2/3 成功，总有效运行通过率至少 85%；同模型客户端对照若落后超过 10 个百分点，必须定位原因并列入修复。P0 可据样本难度调整一次并记录理由，首次正式测评开始后冻结标准，不能看完结果再降低。
- 任何数据丢失、串账号、越权写入、审批后内容被偷换或重复外发均是阻断问题，不以总分抵消。D08–D10 的状态、取消与权限不变量须全部通过确定性测试。

OpenAI 公开 App Server 文档列出 thread/resume 和 turn/steer，后者绑定当前 turn 且不能同时更换模型 / cwd；计划以此作为接口核验方向，而不是假定本项目锁定版本全量支持。[官方 App Server 文档](https://learn.chatgpt.com/docs/app-server)

Codex 的变更查看支持检查仓库 diff 及针对变更给反馈，因此本轮对照包含“改完能核验”的体验，不只看代码生成。[官方代码审查文档](https://learn.chatgpt.com/docs/code-review?surface=app)

### 6.5 性能验收

- 本地受理反馈目标：基准机器上提交后 200ms 内出现已受理 / 等待状态；停止点击 200ms 内显示取消中。以 UI 测量为准，网络或引擎完全停止另记耗时，不混算。
- 每种关键聊天路径冷 / 热启动各至少 10 次，报告中位数、范围和样本数；小样本不将 P95 当可靠结论，出现长尾后扩大采样。
- 对比相同短提示、历史长度、工具数量及账号配置。记录本地准备与请求后模型时间；重点减少重复启动 / 探测，不承诺所有模型固定秒数返回。
- 热路径本地开销目标可暂设比同条件基线降低 30%；若基线已很低或瓶颈在上游，转为消除可确认的重复工作并报告实际结果，不制造改善数据。
- 长会话按实际消息量测滚动、增量更新和恢复时间；分页不丢队列或审批状态。关闭无关插件后不出现对应进程 / 网络请求。

## 7. 缺陷修复和发布门槛

缺陷分级：阻断 = 数据 / 凭据 / 权限问题与重复副作用；高优先级 = 无法聊天、修改项目失败、认证假成功、取消失效；一般 = 回显、可用性、性能和细节。性能导致无法工作时提升优先级。

每个缺陷记录：任务编号、复现输入、环境 / 版本、预期 / 实际、证据、根因、修复提交和复测结果。能固定复现的加入回归；一次上游失败不靠无限重试掩盖，也不无依据归因于网络。

发布门槛：

1. 迁移、类型检查、相关逻辑 / 协议测试与完整 Electron 回归通过；禁止丢失旧聊天、自定义角色或认证引用。
2. 聊天 C01–C10 中本阶段支持的能力通过，未支持组合明确标记；普通聊天、上下文续接和项目基础修改不存在未解决高优先级缺陷。
3. 真实项目测试达到冻结后的标准，对照差距公开；没有完成真实模型验证的组合不得贴“已验证兼容”。
4. 至少交付平台完成安装包实机回归；Mac 未实测时不能以“双平台完整支持”发布，需保持平台待验状态并继续该工作包。
5. 渠道逐平台具备真实发送证据或保持未验证；扫码接入有实际授权与消息权限结果。远端平台暂不可用不能把本轮相关待办标为完成。
6. README / 能力矩阵 / 迁移说明与实际一致，GitHub 对应代码和构建版本可核对；本地测试数据和凭据不进入仓库。

下表为单人串行有效工作日估算，包含实现和阶段验证，不含等待第三方应用审核、账号 / Mac 设备到位及签名证书的时间。用于安排顺序，不能视为交付日期承诺；P0 后按已确认的协议能力修订。
