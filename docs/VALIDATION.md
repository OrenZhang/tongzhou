## 聊天延迟样本

使用 `scripts/chat-latency-smoke.mjs` 的测试流程，同一 Kimi 账号 / 模型，10 个独立新会话各做一次短输入及一次记忆续聊，20 轮全部完成且无串线。新会话是新原生引擎会话，整个桌面程序保持打开，不是 10 次系统冷启动。

| 测量                             | 样本 | 中位数  | 范围          |
| -------------------------------- | ---- | ------- | ------------- |
| 新会话总完成时间                 | 10   | 4.687s  | 2.960–13.570s |
| 同会话续聊总完成时间             | 10   | 2.144s  | 1.618–5.065s  |
| 新会话到“等待模型响应”的本地准备 | 10   | 924.5ms | 882–944ms     |
| 续聊到“等待模型响应”的本地准备   | 10   | 27.5ms  | 14–35ms       |
| Run IPC 返回                     | 20   | 28.5ms  | 17–39ms       |

总耗时含网络与模型生成，采用约 250ms 轮询完成状态。IPC 耗时不是界面渲染延迟，也不是首字延迟；本轮没有将其包装成“UI 200ms / 首字秒回”验收。样本规模只支持描述统计，不给稳定 P95 保证，不外推到其他账号或模型。热会话准备时间减少，来自省去重复引擎启动；新会话仍有模型侧长尾。

设置与真实编程测试相同的 `TONGZHOU_LIVE_CODING`、`TONGZHOU_NATIVE_SOURCE` 和 `TONGZHOU_TEST_ENGINE` 后运行 `npm run test:latency`。原始测量在被忽略的 `test-results/` 内。
